- **`terminal.GetMousePos()` returns raw VIRTUAL-DESKTOP coordinates spanning
  every monitor, while `terminal.desktop.box` is the game window's own display
  only. On a multi-monitor setup these are different coordinate spaces**, and
  every cursor position on a non-game monitor is outside `desktop.box` by
  construction (MEASURED 2026-08-04, co-run #1 — logs
  `docs/archive/corun1_Mars.exe-20260804-12.42.47.log`,
  `corun1c_Mars.exe-20260804-13.23.08.log`).

  Measured setup: display 1 `3840×2160` at `(0,0)` (game fullscreen here),
  display 2 `3840×2560` at `(3840,0)`, virtual desktop `0..7680 × 0..2560`.
  The game read `desktop.box (0,0)-(3840,2160)`, `screen (3840,2160)`,
  `UIL.GetSafeArea() = 0 0 3840 2160` — **exactly display 1** — while
  `GetMousePos` returned `x` up to **7665** and `y` up to **2559**. Every number
  closes to the pixel against the physical layout.

- ⛔ **Consequence for any UI that anchors on the mouse.** Feeding such an
  anchor to a layout that clamps against the safe area does **not** produce a
  small error: the clamps pin the window to the screen edge, arbitrarily far
  from where the cursor appears to be. MEASURED on the shipped
  `ResourceItems` picker: anchor `(5305,2269)` (both axes out of range) put the
  dialog at **`(2224,1731)-(3840,2160)`** — the bottom-right corner —
  reproducing a prediction computed from `ResourceItems.lua:45-71` before the
  run. With only `x` out of range, only the x clamp fires and the result is
  right-edge rather than corner. Live example and disposition: `agent/bugs/C41.md`.

- ⚠️ **This does NOT mean the two spaces disagree in general.** For an
  **in-range** anchor they are the same space and vanilla places the dialog
  exactly on the cursor — that is what F76's M1/M2 measured, and it is why
  F76's "coordinate-space mismatch" mechanism was correctly refuted. The
  divergence is a *multi-monitor* property, not a scaling one. ⛔ **So a repair
  that "converts" the anchor unconditionally would break the ordinary case**;
  the only defensible shape is to detect out-of-`desktop.box` and clamp or
  re-read, not to transform every anchor.

- ⚠️ **Measurement hazard that produced a false record here.** An OS-side
  monitor read taken from a **non-DPI-aware** process returns *logical* units,
  not pixels — a PowerShell `System.Windows.Forms.Screen` read returned
  `2560×1440` / `2560×1707` for these displays because Windows was at 150%
  (`3840/1.5 = 2560`). That was briefly filed as an unexplained three-way
  coordinate disagreement. **An OS-side measurement from a non-DPI-aware
  process is not a measurement**, in the same way an on-screen console reading
  is not a reading. See [[EF-045]] for the sibling "the harness cannot time
  itself" trap from the same rig.
