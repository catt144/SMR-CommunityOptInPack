- ⭐ **Why this is worth a fact rather than a report line: neither surface is
  visible to any census of our own code.** The L4 player-surface sweep
  enumerated 17 screen call sites in `Code/` and concluded the pack "mints no
  notification, popup, banner or voice line of its own". That is true and it is
  not the whole player experience — **on the failure path the engine raises the
  surface, keyed on our mod's `content_path`, with no call site of ours
  involved.**

- **(a) The runtime surface — `ReportModLuaError`** (`CommonLua/Classes/Mod.lua`):
  ```lua
  if not Platform.asserts then          -- :2951, so RETAIL takes this branch
  function ReportModLuaError(mod, err, stack)          -- :2958
      if config.DisableErrorReporting then return end  -- the only off switch
      if ReportedMods[mod.id] then return end          -- once per id per process
      …
      ModPrint("Error in mod %s (id %s, v%s) from %s", …)        -- :2981
      CreateMessageBox(false, T(6902, "Warning"), err)           -- :2992
  end
  function OnMsg.OnLuaError(err, stack, os_paths)      -- :3001
      for _, mod in ipairs(ModsLoaded) do
          if string.find_lower(err, path) or string.find_lower(stack, path) then
              ReportModLuaError(mod, err, stack)
          end
      end
  end
  ```
  The box text is `T(12646)` + `T(796336029093, "Mod Flagged")` + the mod title.
  ⚠️ **The match is a substring test on the STACK**, so an error thrown in
  *vanilla* code that our wrapper called flags us just as readily as one thrown
  in our own body.
- **(b) The load-time surface.** Each `Code/*.lua` is executed by `pdofile`
  (`lib.lua:242-251` — `pcall(loadfile(...))`), so a file-scope throw aborts
  **only that file** and the other 75 still load. The error is collected by
  `ModDef:LoadCode` (`Mod.lua:490-520`) and `ModsLoadCode` (`:2254-2275`) both
  `ModLog`s `Errors while loading mod <title>:` **and** builds
  `ModsLoadCodeErrorsMessage`.
  ⛔⛔ **CORRECTED 2026-08-19 (terminal audit): that message box NEVER DISPLAYS
  on this title.** Its two display routes are `OnMsg.PreGameMenuOpen`
  (`Mod.lua:2231-2243`) — a Msg raised only by `CommonLua/UI/MainMenu.lua:15`,
  which SM's `Lua/init.lua:1` override never calls (the same dead-Msg mechanism
  EF-055 documents) — and the `ModsPreGameMenuOpen` flag (`:2271`), initialized
  false (`:2224`) and set true nowhere in the tree. ⇒ **a file-scope throw is
  LOG-ONLY; a player whose install loses modules this way is told nothing.**
  The pack's own C1 dialog is likewise blind to it — see the next clause.
  ⚠️ **Nuance on registry state (measured, L8 harness):** a module is ABSENT
  from `SMRFixPack.fixes`/`order` only when the throw precedes its `Register`
  call. A throw **inside** `Register` after the entry is stored (the L8-F1
  shape at `00_Core.lua:446`) leaves the id present with status `pending` —
  a status `UpdateSuspects` (:521-541) never inspects. Either way no surface
  of ours reports it.
- ⭐ **`content_path` is configuration-invariant** (closes the packed question
  this fact carried): both mount branches converge on
  `def.content_path = ModContentPath .. def.id .. "/"` (`Mod.lua:1755-1758`,
  `ModContentPath = "Mod/"` at `:6`), so the (a) substring match reads
  `Mod/SMR_CommunityFixPack/` in run B exactly as unpacked — re-derived by the
  L7 link and re-verified by the terminal audit's fan-out.
