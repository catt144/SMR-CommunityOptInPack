- **SOURCE — what the sync does to `AccountStorage.LoadMods`.** `OnMsg.PdxLogin` pushes `SyncPdxMods`
  on `g_PopsDownloadModsQueue` (`CommonLua/UI/ModManager.lua:1902-1906`); the root fetches the
  subscriptions and pushes one `SyncUpdatePdxMod` per subscribed or installed mod (`:1864-1885`).
  The child finds the def by `v.PdxMod.ModID` and, on a version change, runs `mod_def:delete()` and
  `TurnModOff(mod_def.id)` (`:1798-1801`); after an install it sets `mod_entry.Enabled` only
  (`:1855-1860`). `TurnModOff` removes one id and `TurnModOn` appends (`:35-41`), so a mod without a
  `PdxMod` (a Steam or junction install) is never moved, and a moved Paradox mod comes back at the
  end of the list through `SetEnabledAndSync` (`:1532-1550`) or `OnMsg.PdxModInstalled` (`:1930-1951`).
- **SOURCE — the sync's result cannot be read by a mod.** `AsyncPdxGetAllSubscribedMods` tests
  `#new_mods == 0` before `err` (`:1739-1760`), so a failed first page that comes back empty returns
  `false, {}` and `SyncPdxMods` prints nothing; install and uninstall failures are printed, not
  returned (`:1802-1807`, `:1825-1833`). `AsyncPdx`, `Pops` and `PDX` are blacklisted prefixes
  (`CommonLua/Libs/Paradox/ParadoxMods.lua:288-294`), so a mod cannot repeat the fetch. What a mod
  can see is the queue instance (`g_PopsDownloadModsQueue`, reachable: `g_` is no prefix) and the
  callbacks' start, return, raise or string return.
- **OBSERVED — this rig, 2026-09-26.** `PdxLogin` fires at every boot through the SDK's auto-login
  (`PdxSDK.lua:333-338`); the root runs about 115 ms and returns with zero children on every launch
  (logs L12, L13, sitting S1–S6, `docs/archive/load_order_first_audit4_2026-09-26/` and
  `load_order_first_sitting_2026-09-26/`), and a log-out plus log-in runs a second root the same
  way (S5 :355–407). The rig has no Paradox-installed mod (`PdxMods` holds only `temp_pdx`), so the
  empty result is consistent but not proof of an empty account: an empty attempt is unverified.
- **CONSEQUENCE for the pack.** LoadFirst promotes at startup and on the option's activation, not
  after a list edit (`Code/01_LoadFirst.lua`). A Paradox-installed copy that the boot sync updates
  is taken off the list, re-added last by the player's tick or the download handler, loads last
  once, and promotes itself again with the notice at the next start (designed, R1). Release notes
  should say so. Reports: `docs/agent/reports/LOAD_ORDER_FIRST_BUILD_2026-09-25.md` §15–§17.
- **CONTROL.** Desk: `python tools/desk_load_first.py` groups `pdxfetch` (a failed empty first
  page returns `err=False`, a populated page returns the mod) and `R5D7` (the archived fetch, root
  and child bodies with failing APIs return normally). Live: arm `tools/arming/legs/load-first-sync.json`
  in `MODE = "unattended"` and boot; this fact holds if the log shows `MSG PdxLogin` followed by
  `PUSH serial=1 kind=root` and an `END … returned=nil` with no child, and fails if a child push
  names a mod that has no `PdxMod`, or if a mod-side `AsyncPdxGetAllSubscribedMods` call resolves.
