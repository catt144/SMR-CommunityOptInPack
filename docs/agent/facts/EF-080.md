- ⭐ **THE BLOCK IS TWO CONFIG VALUES.** (Source-read 2026-09-08, 1.1.0 tree.)
  `Lua/Config/config.lua:174-175`:
  ```lua
  -- the game can't be loaded if the savegame revision is less than it
  config.SupportedSavegameLuaRevision = 402200
  config.OldSavegameBehavior = Platform.steam and "block" or "warn"
  ```
  Our 1.0.7 saves carry `lua_revision` **396349**; the floor is **402200**;
  1.1.0 itself is **403908**. ⇒ blocked.
- ⭐ **THE DEVS SHIP AN UNBLOCKED MODE — WE JUST ARE NOT IN IT.** The gate
  (`CommonLua/SavegameMetadata.lua:154-170`) reads:
  `if load_anyway_enabled or config.OldSavegameBehavior ~= "block" then` → it
  swaps the refusal text for a **`WaitMultiChoiceQuestion` offering "Load
  anyway" / "Cancel"**. `load_anyway_enabled = Platform.developer` (`:123`).
  So on any non-Steam platform the same build already offers the load. The red
  **"Deprecated save file format!"** label is likewise gated on
  `config.OldSavegameBehavior == "block"` (`Lua/UI/SaveLoad.lua:76`;
  `CommonLua/UI/SaveLoadUI.lua:300`).
- **Two runtime overrides, either sufficient, neither touching a game file:**
  1. `config.OldSavegameBehavior = "warn"` → the refusal becomes a "Load anyway"
     prompt, and the red label disappears.
  2. `config.SupportedSavegameLuaRevision = <= 396349` → the gate never fires.
  `config` is a plain table reachable from mod code, so this is the same class of
  runtime edit the pack already performs — **no game directory modification, and
  therefore not a breach of that binding.**
- ⛔ **WHY THIS MUST NOT BECOME A HABIT — THE ARGUMENT IS ABOUT EVIDENCE, NOT
  RISK APPETITE.** 402200 is not "one revision back"; it sits deliberately
  BETWEEN 1.0.7 (396349) and 1.1.0 (403908), i.e. **after the research and
  services systems were replaced wholesale**. A force-loaded 1.0.7 colony
  therefore carries legacy state for two systems that no longer exist in that
  form. Whatever `SavegameFixups.*` migrate, the devs drew the supported line
  above it. ⇒ **any anomaly observed on such a colony cannot be attributed** —
  mod, or half-migrated save, and no control distinguishes them. That is exactly
  the confound a fixture exists to prevent.
- **The rules that follow, and they are not negotiable:**
  - ✅ **Legitimate:** triage and *exploration* — "does anything obviously
    explode", reading state out of an old colony, recovering information.
  - ⛔ **Never a verdict.** No A/B, no status change, no `tested-*`, no entry
    conclusion may rest on a force-loaded save.
  - ⛔ **Never in the shipped pack.** A published mod that unblocks the devs'
    save gate would let players load saves the developers refused, and every
    resulting corruption would be blamed on us. If this is ever built it belongs
    in the **TestKit, which is local-only BY DESIGN**.
  - ⛔ **Never save over a fixture.** Saving a force-loaded colony writes a
    1.1.0-format file over a save only the 1.0.7 branch can otherwise read —
    destroying an irreplaceable fixture (`EF-079`).
  - ⚠️ `EF-056` still binds: a copy-load still runs autosave rotation and
    deletes autosaves. Pre-copy first.
- ⚖️ **The honest comparison** (decision 98): switching the install to the 1.0.7
  branch costs a ~10 GB re-download and gives **attributable** results on the
  whole fixture library; a config override costs one line and gives results no
  one may rely on. They are not substitutes.
