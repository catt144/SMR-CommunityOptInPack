- ⚠️ **A DELIVERY IN FLIGHT IS RE-OPENED BY `Drone:ImproveDemandRequest`
  TOWARD ANY STRICTLY-HIGHER-BAND DEMAND OF THE SAME RESOURCE.** (Source-read
  2026-09-01, the bands report's review — the gap the report's V/R11 row
  missed.) `Drone:Deliver` (`Lua/Units/Drone.lua:1164-1175`) calls
  `self:ImproveDemandRequest(…)` for every delivery that came from `PickUp`
  unless `do_not_improve_req` is passed — and the shipped `PickUp` tail chains
  `SetCommand("Deliver", d_request)` WITHOUT it (`:1013-1014`).
  `ImproveDemandRequest` (`:760-812`) computes `priority =
  d_building:GetPriorityForRequest(d_request) + 1` (`:766`) and asks
  `FindDemandRequest(self, resource, amount, priority, ignore_flags)` for a
  strictly better destination in the REAL demand queues, unassigning the
  original on success (`:790-796`). **Consequence for urgency designs:** a
  demand elevated only OUTSIDE the real queues (a view tier, a substituted
  pairing) still carries its real band in `GetPriorityForRequest`, so the
  parts flown for a tier-5 repair can be traded up mid-flight to any routine
  band-3 demand — the exact inversion the tiers exist to prevent. Guard the
  seam: a chained wrapper on `ImproveDemandRequest` (synchronous — finders +
  claim arithmetic, no yield in the body) that declines improvement while
  `d_request` is tier-tracked, or pass the vanilla `do_not_improve_req` seam.
  Vanilla baseline for scale: band-2 deliveries are ALREADY hijackable by
  band-3 demands today — the trap is only that tier designs think they
  outrank 3 and this seam does not know it. E-8's card must assert the guard
  (a tier delivery arrives at the tier building). Cross-refs: `EF-060` (the
  finders), opt-in `reports/DRONE_BANDS_CLEAN_REVERT_20260901.md` §4.2/§5.
- ⚖️ **AMENDED 2026-09-01 (opt-in `reports/DRONE_REBUILD_DESIGN_20260901.md` §2b
  rule 5) — THE GUARD NEEDS A `must_change` CARVE-OUT OR IT HANGS THE DRONE, and
  the `do_not_improve_req` half of the sentence above is not reachable without
  replacing a command body.** (Source-read 2026-09-01.) `Deliver`'s retry loop
  sets `must_change` when the destination is unreachable, when a fulfill retry
  failed, or when the request was suspended (`Drone.lua:1246-1250`), and passes it
  into `ImproveDemandRequest` at `:1253`. A guard that declined improvement
  UNCONDITIONALLY would return the same unreachable `d_request` every pass and the
  drone would loop at `Sleep(1000)` forever. ⇒ **decline only while `must_change`
  is false; hand `must_change` calls straight to `orig`** — which is also vanilla's
  own escape hatch (`:1254-1257` drops the request when improvement is off). The
  declining return is then byte-equivalent to vanilla's own "nothing better found"
  outcome: with `must_change` false and `assigned` still true the shipped body
  falls to `:807-812` and `return d_request` with the drone still assigned, so the
  wrapper NARROWS an existing result rather than inventing one (`FIX_POLICY` §1.4b
  shape). ⛔ **The `do_not_improve_req` route is NOT available to a mod**: the flag
  is a `Deliver` parameter and the only caller that would have to pass it is
  `PickUp`'s tail (`:1013-1014`), inside a command body with `Sleep`s — reaching it
  means a §1.5 full replacement of `Drone:PickUp`. A pre-wrapper on `Drone:Deliver`
  that forces the flag is layer-2-shaped but puts the tier state in a frame that
  sits above `Deliver`'s own `Sleep`s (`EF-023` route (b)); the
  `ImproveDemandRequest` wrapper is synchronous and does not. **Membership needs no
  mod table:** `local b = d_request:GetSource(self); IsValid(b) and
  b.is_malfunctioned and d_request == b.maintenance_resource_request` is computed
  entirely from vanilla fields.
