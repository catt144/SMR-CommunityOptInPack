- ⛔⛔ **ON AN *UPDATE* UPLOAD, THE VERSION ARITHMETIC CANNOT TELL YOU WHICH
  PORTALS RAN — one sitting produces ONE bump even when BOTH portals are
  uploaded.** (Source-read + measured 2026-08-29, after the owner refuted a
  finding built on the opposite assumption.)
  * **The route, re-read at Src.** `Steam_PrepareForUpload`
    (`CommonLua/Platforms/steam/SteamWorkshop.lua:1-36`) does this:
    ```lua
    if mod.steam_id == 0 then
        ... AsyncSteamWorkshopCreateItem()
        params.publish = true
        mod:SaveWholeMod()      -- the bump, INSIDE the create-item branch
    else
        params.publish = false  -- an UPDATE: no save, no bump
    end
    ```
    ⇒ the forced pre-pack save happens **only when the Workshop item is being
    created**. On every later upload `steam_id` is already set and non-zero, the
    ownership probe confirms the item `exists`, and the `else` runs.
  * Paradox's `mod:SaveWholeMod()` (`ParadoxMods.lua:173`) is **unconditional**,
    after the upload returns. ⇒ **one save per sitting, Paradox's**, and if Steam
    is uploaded second it packs the tree as that save left it.
  * ⛔ **THE TRAP, and it caught a session.** `reports/RELEASE_PORTAL_PREP.md`
    §0.5(c) tabulates "when each portal saves" — correctly, and its own prose says
    *"Both portals call `SaveWholeMod()` unavoidably on a **first** upload"*. On
    2026-08-29 a session read one bump per sitting as proof that **only** Paradox
    had run, and filed "Steam has neither F105 nor F108" as an owner decision.
    It had run, at both sittings. A first-upload rule was generalised to updates,
    with the word "first" in the citation being quoted.
  * ⭐ **THE CONTROLS THAT ACTUALLY SETTLE IT.** (1) The store's own change-notes
    page — the Workshop listing showed three updates, **Aug 20 / Aug 24 / Aug 28**,
    the last two matching `saved` to the minute (1787608530 = 08-24 17:55 local;
    1787956898 = 08-28 18:41 local). (2) **Subscribe and read the delivered
    archive** — the definitive one, because it is what a player receives.
  * **Measured off the subscribed copy 2026-08-29**
    (`steamapps/workshop/content/3215050/3787202810/ModContent.fpk`, 396,408 B,
    md5 `af58c31e07e8586e2b2f31a913eeff7f`): **84 entries** (80 `Code/*.lua` +
    `items.lua` + `metadata.lua` + `LICENSE` + `preview.png`), **82 of 84
    byte-identical** to our tree — the 2 that differ are `items.lua` and
    `metadata.lua`, exactly the comment-stripping. Both disputed modules are
    present: `Fix_LandscapeCostRefresh.lua` (F105) and
    `Fix_ExtractorStaffedPerformance.lua` (F108). Its packed `metadata.lua` reads
    `version` **4**, `pdx_version` **"3"** — the tree's own values, confirming
    Steam packed AFTER Paradox's save.
  * ⚠️ **`pdx_version` is NOT our version.** `mod.pdx_version = res.Version`
    (`ParadoxMods.lua:172`) is the number the PORTAL returns — its own revision
    counter (1, 2, 3 across our three uploads). What the Paradox page shows as
    MOD VER is a different field, `VersionDisplayName = tostring(mod.version)`
    sent at `:156`, i.e. the version **before** `:173`'s save bumps it. Two
    successive comment glosses in `metadata.lua` had this wrong.
  * ⇒ **Consequence for the portal-gap worry.** Because an update sitting bumps
    once and Steam packs after it, both listings now carry the same code at
    `version = 4`; the page numbers can still differ by one, for the `:156`
    reason above. ⛔ Do not chase it (checklist 71).
