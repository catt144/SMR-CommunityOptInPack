- ⚠️ **THE C MATCHER READS THE PRIORITY BOUND FROM THE `const.TaskRequest`
  GROUP — NOT FROM THE KEYS OF THE TABLES IT IS HANDED.** (Measured 2026-07-31,
  re-read 2026-09-01 with the recovered experiment source; MEASURED-then-INFERRED
  — the inference step is written out here and its falsifier is experiment E-4,
  opt-in `reports/DRONE_BANDS_CLEAN_REVERT_20260901.md` §5.) The evidence: the
  v1 Q1/Q2 experiment (TestKit `f617576:Code/97_Q1Q2_PriorityBands.lua:88-110`)
  set `const.TaskRequest.MaxBuildingPriority = 5` at file scope and — its own
  header says so — left the flat `const.MaxBuildingPriority` at its baked 3;
  on an existing save every `FindTask` then threw `attempt to index a nil value`
  at `[C](-1)` over hubs whose tables were `-1..3` (`DRONE_PRIORITY_SYSTEM.md`
  §8). A `lua_next`-style walk of existing keys cannot index an absent key, and
  `#t` on a `-1..3` table cannot reach 4 — so C iterated an explicit range whose
  upper bound came from OUTSIDE the tables, and the only external value that had
  changed was the group. Corroboration (SOURCE, historical): Haemimont's 2018
  public Lua mirror of the matcher iterates `for j = MaxBuildingPriority, -1, -1`
  (HaemimontGames/SurvivingMars, `Lua/Buildings/DroneHub.lua:441-621`).
  **Open, and NOT to be assumed:** whether C reads the group at CALL TIME or
  caches it at `ClassesPreprocess` — E-4(ii) decides; a per-call bound flip
  (design V-b) is valid only if call-time. **Consequence:** a "shadow view" with
  keys 4/5 under a const of 3 is never looked at; conversely a widened const
  over ANY un-topped-up hub is the §8 crash. Cross-refs: `EF-072` (what
  `FindTask` passes), `DRONE_PRIORITY_SYSTEM.md` §8.
