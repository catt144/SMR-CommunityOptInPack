- **The route, re-derived from Src 2026-08-12** (chain `split-optins`, prompt 3;
  first pinned by the chain's QA gate and re-walked here rather than inherited):

  ```
  GetModsToLoad()        Mod.lua:1992   list = table.icopy(AccountStorage.LoadMods)
                                        -- ⚠️ unless AccountStorage.LoadAllMods or
                                        --    config.LoadAllMods, :1988-1991, in which
                                        --    case list = table.keys(Mods) + table.sort
    -> GetLoadingQueue(list)  :1894      DFS over `list` IN ORDER; a mod is appended
                                         after its declared dependencies, so with no
                                         dependencies the queue IS the list
  ModsReloadItems()      :2110-2114     ModsLoaded[#+1] = Mods[id], for i,id in ipairs(queue)
  ModsLoadCode()         :2256          for _, mod in ipairs(ModsLoaded) do mod:LoadCode()
  ```

- ⇒ **Between two mods, whichever the account enabled FIRST loads first**, and its
  wrappers therefore sit INNERMOST when both wrap the same function. The order is
  stable per account and survives restarts (it lives in account storage), but it is
  not something a mod can declare, request or detect ahead of its own load.

- ⚠️ **`Mod.lua:490-521` is the OTHER order and must not be confused with this one:**
  `ModDef:LoadCode` iterates `ipairs(self.code)`, so INTRA-mod file order is the
  `metadata.lua` `code` list's order and scans no directory. Two different orderings,
  two different sources — intra-mod is ours to set, inter-mod is not.

- ⇒ **Design consequence, and it is why this fact was pinned:** a companion mod may
  not assume it loads after (or before) another. Both the Community Fix Pack and the
  Community Opt-In Pack wrap `UniversalRocketBase:GetFuelResourceRequest` and
  `Drone:CleanUnreachables`; each pair was shown order-independent by construction
  (mutually exclusive conditions in the first, pre-wrapper vs post-wrapper in the
  second) rather than by assuming a load order.

- ⭐ **AMENDED 2026-08-16 — the two mechanics that answer "how does a PLAYER set
  it", re-derived at Src the same day and confirming everything above:**
  * **Enabling APPENDS.** `table.insert_unique(AccountStorage.LoadMods, id)`
    (`CommonLua/UI/ModManager.lua:36`); disabling removes it (`:40`);
    "disable all" is `table.clear` (`:44`). ⇒ The only player-side lever is
    *disable and re-enable*, which moves a mod to the END of the list and
    therefore to the OUTERMOST wrapper position. There is no reorder control in
    the UI because appending on enable IS the interface.
  * ⛔ **The visible list is a COSMETIC sort and is NOT this order.**
    `SortModsList` (`Mod.lua:1674-1683`) sorts `ModsList` — the display list —
    by items-loaded then `title`, and never touches `LoadMods`. ⇒ A player
    following any load-order advice **cannot see whether it worked**, which is
    why no such advice is on the player-facing pages.

- ⚖️ **WHY FIRST IS THE PREFERRED POSITION FOR THE FIX PACK — the design intent,
  recorded 2026-08-16 because it existed only in the owner's head** (their
  words: *"our original reason for loading first was to just fix vanilla to make
  sure we aren't over writing mods that make changes to the things we fix"*):
  loading FIRST makes our wrapper INNERMOST, so we patch the **vanilla** we
  verified against `Packs\Lua.fpk`, every later mod wraps US, and a mod that
  REPLACES the function outright simply wins — our fix vanishes cleanly, which
  is the correct outcome when someone deliberately reworks a system we merely
  repaired. **The inverse is the harmful one:** loading LAST would wrap another
  mod's implementation and apply a vanilla-derived fix on top of code we never
  inspected — precisely what §"verify the target" exists to prevent. Same
  direction for data-shaped patches: patch early, let a later mod's template
  edit overwrite ours.
  ⛔⛔ **BUT IT IS A PREFERENCE, NOT A REQUIREMENT, AND NOTHING MAY BE BUILT ON
  IT.** The deference is already achieved BY CONSTRUCTION (layer-3 wrappers that
  call through, plus the order-independence this fact forces). Nothing breaks if
  the pack loads third. ⚖️ **OWNER RULING 2026-08-16: *"lets note this and see if
  it ends up being a problem before we create new problems"*** — so: no player
  instruction, no `for-modders.md` change, no playtest item filed. If a real
  ordering conflict ever appears in the wild, this bullet is the head start;
  until then the silence on the public pages is deliberate and correct.
