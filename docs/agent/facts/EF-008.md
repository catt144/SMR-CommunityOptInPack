- **`error()` and `assert()` do NOT unwind mod code — they report and execution
  continues** with the next statement (LuaExports.lua:567 "asserts pop instead of
  being printed out"). Never use them for control flow; `pcall` still catches
  genuine runtime errors. Cost us four bogus FAILs and ten ERRORs in the first
  A/B pair (see the diagnosis section).
- ⚠️ **SCOPE NOTE 2026-08-19 (pre-launch sweep, link 6): this fact carries no
  build qualifier, and the engine's own comments say the behaviour has one.**
  `autorun.lua:243` — *"Platform.asserts is set in all debug builds (see C macros
  DBG_ASSERT_ENABLED)"* — and `Mod.lua:2951` gates the player-facing mod-error UI
  on `if not Platform.asserts`, i.e. it exists **because** retail has no asserts.
  This project's only measurement of an assert reaching a log is `C43`, taken on
  **MarsDebug**; the 74 retail logs are **not a control**, because the code that
  produced it was fixed before any retail run touched it — the condition was never
  sampled. ⛔ **Nothing here is reversed** — the guidance ("never use them for
  control flow") is right whether or not retail prints anything, and is arguably
  more important if retail is silent. What is open: **whether an assert in mod
  code REPORTS at all in a retail build.** Settling it needs mod code that trips
  one, which the pre-launch chain bars. `reports/L6_PROMISE_MAP.md` §4.
