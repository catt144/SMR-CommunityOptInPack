- ⭐ **THE CLAIM THIS RECORDS, AND WHY IT NEEDED A HOME.** The `smrcf-text` chain
  (chain B of `prompts/SMRCF_CHAIN_SET.md`) carried a "dust-devil marker gate" as
  a rider, described there as: *"the marker thread checks `HasDustStorm` and omits
  `DustStormsDisabled`; the natural scheduler checks both, twice, in the same
  file."* It was the chain's last live item — `C50` and `C51` were built in
  1.0.0 and their modules later deleted — and it was recorded nowhere except
  inside that chain's own folder. Measured 2026-09-09 at the owner's question
  *"for that rider are we sure that is still a problem in 1.1?"*
- ✅ **THE FINDING WAS TRUE ON 1.0.7. This half matters** — without it, the
  refutation below reads as the original observation having been sloppy, and it
  was not. `C:\Dev\SMR-SrcArchive\1.0.7.396349\Src\Lua\DustDevils.lua:169`:
  ```lua
  if not HasDustStorm(map) and SessionRandom:Random(100) < descr.marker_spawn_chance then
  ```
  `HasDustStorm` only. The natural scheduler in the same file, at `:209` and
  `:220`, both read `HasDustStorm(map) or DustStormsDisabled`. Two paths, two
  different gates, one file — the sibling inconsistency exactly as filed.
- ⛔ **IT IS FIXED ON 1.1.0.** `Lua/DustDevils.lua:170`, inside
  `WaitSpawnDustDevil(descr, marker)` — the marker path:
  ```lua
  if HasDustStorm(map) or DustStormsDisabled then
      return
  end
  ```
  **Both terms.** The natural scheduler still checks both in two places — `:248`
  in its `idle` branch, and `:267` **negated** when picking a spawn position
  (`local pos = not (HasDustStorm(map) or DustStormsDisabled) and …`). Three
  sites, one gate shape, no disagreement left in the file.
- **The path was RESTRUCTURED, not incidentally edited**, which is why this reads
  as a deliberate repair rather than a coincidence: 1.0.7's single compound `if`
  became an early-return guard at `:170` plus a SEPARATE chance check at `:174`,
  and the file grew 18306 → 21074 bytes between branches.
- ⚖️ **WHAT IS MEASURED AND WHAT IS NOT.** Measured: the source text of both
  branches, read two-sided off the two trees on disk. NOT measured: any in-game
  behaviour on either branch — nobody has watched a marker dust devil spawn or
  fail to spawn with `DustStormsDisabled` true. The claim is about the GATE's
  shape, which is what the rider was about; a behavioural check was never the
  rider's bar either, because the rider's own precondition was a
  `PrefabFeatureMarker` census that was never run.
- ⇒ **CONSEQUENCES, both of which retire work.**
  1. The `smrcf-text` rider is **refuted**; chain B has nothing owed and can be
     consumed.
  2. **Chain A (`smrcf-verify`) job 1 is moot with it.** That job existed to

     decide whether the rider was worth building. The defect is gone, so
