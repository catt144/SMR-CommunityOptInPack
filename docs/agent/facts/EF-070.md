- ⚠️ **AUTOSAVE AND QUICKSAVE RUN WITH GAME TIME UNPAUSED, AND ≥ 4 YIELDS SIT
  BETWEEN `Msg("SaveGameStart")` AND THE PERSIST WALK.** (Source-read 2026-09-01,
  `BANDS_CLEAN_REVERT` delta 15; route re-verified independently the same day.)
  `DoSaveGame` (`CommonLua/Savegame.lua:1037-1063`) fires `Msg("SaveGameStart",
  params)` at `:1043`, then reaches `EngineSaveGame` (`:862`, inside `PersistGame`)
  only through `Savegame.WithName`/`WithTag` → `Savegame._Wrap` (`:337-344`),
  which `WaitThread`s a fresh real-time thread, `_InternalSave` (`:346-372`,
  `AsyncStringToFile` among others), and `GameSpecificSaveCallback` (`:1006-1023`,
  `WaitRenderMode` on the screenshot path). The silent-save screen used by
  autosave/quicksave is NOT game-blocking (`SilentSaveScreen.generated.lua:20`,
  `game_blocking = false`); only the manual save dialog path opens a blocking
  screen. ⇒ between a `SaveGameStart` handler returning and the state actually
  being serialised, game-time threads (drones included) can run and mutate what
  the handler prepared. **Consequence:** any tear-down-on-save scheme — a
  handler that normalises mod-shaped state so the save is clean — cannot
  guarantee its invariant on the autosave/quicksave paths; it is sound only
  under a blocking screen (manual save) or for state no game-time thread
  touches. **Two save paths skip BOTH messages:** the in-game bug reporter
  (`SaveGameBugReportPStr :1143` → `GameSpecificSaveCallbackBugReport`) and
  `InMemSaveGame` (`:1119`, no Lua caller found). Cross-refs: `EF-024`/`EF-030`
  (the hooks exist and cover autosaves — unchanged; this fact bounds what a
  handler may safely DO), `EF-023` (what the walk captures).
