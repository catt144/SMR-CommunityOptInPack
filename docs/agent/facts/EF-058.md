- ⚖️ **AMENDED 2026-08-19 (sweep link 8, lens L8) — THE SCOPE CLAUSE THIS FACT
  WAS MISSING, re-derived at Src this session and not inherited.** The trap is
  decided by **when the wrapper is installed relative to class flattening**:
  * mod code executes from `ModsLoadCode()`, a **direct call** at
    `CommonLua/Core/autorun.lua:423`;
  * flattening happens in `classes.lua`'s `function OnMsg.Autorun()`, whose own
    header says *"class tables for which `hierarchy_cache` is true are
    'flattened', containing directly the inherited values from all parents…
    This isn't done for all classes to save memory"*;
  * `Msg("Autorun")` is posted after that block ⇒ **mod load strictly precedes
    flattening.**
  ⇒ A patch installed at a mod file's scope, or inside a `SMRFixPack.Register`
  `apply` (which `Register` calls synchronously at file scope — measured, **75 of
  75** `Register` calls are at column 0), lands on the classdef **before** the
  copy-down, so flattening propagates OUR function into the subclasses. The fix
  pack's **50** method patch sites are all of that kind and are safe **by
  construction**, not by luck.
  ⛔ **This weakens nothing.** All four recorded bites — the c48-pairing wrapper,
  the wave-11 probe rawget, the sampler class read, `EF-057`'s note — were
  **runtime-installed instruments**, i.e. installed after flattening, which is
  where the trap is exactly as live as the rest of this fact says. **The harness
  rule below stands unchanged for anything installed mid-session.**
  ⚠️ What this does NOT cover: a **foreign mod's** subclass declaring its own
  override is invisible to any sweep of `ModTools\Src` (link 1's C1 check, 4,446
  files) — that is an unbounded surface, not a closed one.
- **The measurement.** Leg `c48-pairing` (2026-08-16) installed a log-only
  wrapper on `g_Classes.TaskRequestHub.FindTask` — the sole `function
  Class:FindTask` definition in the shipped tree (`_TaskRequest.lua:72-83`) —
  and its first launch counted **0 calls in 25,184** across a complete
  10-game-hour window (`archive/c48pair1_*`). Nothing was broken: callers
  invoke `command_center:FindTask(...)`, instance lookup resolves through the
  instance's OWN class (`DroneHub`, `RCRover`, rockets…), and `DefineClass`
  had FLATTENED the inherited function into those class tables as own keys
  ("to save memory this isn't done for all classes…", `classes.lua:988`) — so
  the base-class patch sat outside every live lookup path.
- ⇒ ⛔ **THE HARNESS RULE.** To wrap a shipped method: scan `g_Classes` for
  every class whose `cls.Method` (normal index) is IDENTICAL to the shipped
  function; set the wrapper as an own key on each; remember per class whether
  the key was own (flattened) or inherited, so the restore puts back the
  original or removes the shadow exactly. Then **prove the wiring off live
  instances** — resolve `instance.Method` on the real population and require
  it to be the wrapper — before trusting a single logged number. The repaired
  launch patched **48 classes**, proved **19/19 hubs wired**, then witnessed
  985 pairings (`archive/c48pair2_*`).
- ⚠️ The converse for VALUE fields: writing a class field works when the write
  lands on the exact class the instances belong to (`c48-brake` set
  `VegetationTaskRequester.supply_dist_modifier` and every live instance read
  150) — the trap is asymmetric: reads resolve through flattened copies,
  writes to the wrong table are simply never consulted.
