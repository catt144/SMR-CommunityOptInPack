- ⭐ **THE ASYMMETRY, READ FROM THE SHIPPED 1.1.0 TREE** (`CommonLua/Core/lib.lua`,
  2026-09-08):
  * `GameVar(name, value, meta)` (`:1061-1076`) contains
    `if FirstLoad or rawget(_G, name) == nil then rawset(_G, name, false) end`
    (`:1069-1071`). The KEY is therefore present in the real `_G` from the moment
    the declaring file runs, holding `false` until a game starts.
  * `MapVar(name, value, meta, dont_persist)` (`:984-1000`) appends to `MapVars`,
    sets `MapVarValues[name]` and `PersistableMapVars[name]`, and **never writes
    to `_G`**. The value lives on the map object and is read as `map.<name>`.
  ⇒ `rawget(_G, "X") ~= nil` tells the two apart. `MapVarValues["X"] ~= nil` is
  the same question asked from the other side, and is the engine's OWN
  "already registered" test (`:991`).
- ⚠️ **THIS SHARPENS [[EF-003]], WHICH IS IMPRECISE AS WRITTEN.** EF-003 says
  `g_Consts` "does not exist while mods load". True of the VALUE, false of the
  KEY — and the game's own code makes the distinction visible: `g_Consts` is
  declared `GameVar("g_Consts", function() return Consts:new() end)`
  (`Lua/Modifiers.lua:427`), and the guard two lines below it is
  `return g_Consts and g_Consts[id] or table.get(const, group, id)` (`:432`),
  a TRUTHINESS test under a comment reading "g_Consts does not exist yet".
  ⇒ EF-003's advice (read a GameVar inside the patched function, never in
  `apply()`) is correct and unchanged. What is wrong is inferring from it that
  `rawget(_G, name)` is nil for a GameVar at apply time. It is `false`, which is
  not nil — and `SMRFixPack.Require`'s `{ global = "X", kind = "any" }` form
  tests `v ~= nil` (`00_Core.lua:154`), so it PASSES on a registered GameVar.
- ⭐ **THE ORDERING IS STATIC, WHICH IS WHAT MAKES THE TEST USABLE IN `apply()`.**
  `CommonLua/Core/autorun.lua:432-434`:

      dofolder("Lua")
      DlcsLoadCode()
      ModsLoadCode()

  `dofolder("Lua")` executes the whole game tree, so every top-level
  `GameVar(...)`/`MapVar(...)` call — including
  `Lua/Landscape/Landscaping.lua:19-23` — has run before `ModsLoadCode()` reaches
  a single line of ours. ⛔ This is a DIFFERENT ordering claim from [[EF-001]]:
  the game's files have RUN, but the classes are not yet flattened. Both hold at
  once, and confusing them is how a self-check ends up looking at a classdef.
- ✅ **USED IN ANGER: this is `F115`'s gate.** 1.1.0 moved `Landscapes` from a
  GameVar to `MapVar("Landscapes", {})` (`Landscaping.lua:21`) at the same time
  as it prepended a `map` parameter to `LandscapeForEachUnit` (`:509`). The name
  survived both changes, so a name check is blind; arity is unreadable
  (`debug.getinfo` is absent from the mod sandbox). The asymmetry above is what
  is left, and it is not a proxy — `Landscapes` being absent from `_G` is the
  literal expression the shipped body raises on
  (`attempt to index a nil value (global 'Landscapes')`).
- ⛔ **WHAT IT DOES NOT TELL YOU, STATED SO NOBODY OVERREADS IT.**
  * It detects the STORAGE move, not the SIGNATURE change. The two shipped
    together in 1.1.0; a future patch that changed only one would fool it.
  * A stray global of the same name from another mod defeats the `_G` side.
    Pair it with the `MapVarValues` side when the name is a plausible one for
    someone else to define — registration cannot be faked by a stray global.
  * The 1.0.7 half rests on records, not a re-read: the 1.0.7 tree is gone from
    disk ([[EF-075]]). If `GameVar` did not rawset on 1.0.7, a gate built this
    way also declines there — SAFE, but dead.
