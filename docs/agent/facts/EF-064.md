- ⛔ **The shape, in full** (`CommonLua/PropertyObject.lua:1811-1825`):
  ```lua
  DefineClass.ProtectedPropertyObject = {
  	__parents = {"PropertyObject", },
  	__index = function (table, key)
  		local class = getmetatable(table)
  		local value = rawget(class, key)
  		assert(value ~= nil, string.format("Unknown key '%s' in a protected object '%s'.", key, class.class))
  		return value                       -- :1817 — returns regardless
  	end,
  	__newindex = function (table, key, value)
  		local class = getmetatable(table)
  		local old_value = rawget(class, key)
  		assert(old_value ~= nil, string.format("Creating a new key '%s' in a protected object '%s'.", key, class.class))
  		rawset(table, key, value)          -- :1823 — writes regardless
  	end
  }
  ```
  Both handlers report and then do the thing anyway. There is no `return` or
  `error` between the assert and the effect.
- ⭐ **Combined with `EF-008` this is total.** `assert()` does not unwind mod or
  vanilla Lua in this engine — it reports and execution continues with the next
  statement. So on the write path: the assert fires (in a build where asserts
  are live), `rawset` lands, and the *caller's* following statements run
  normally. **A "protected" object is an undeclared-key WARNING, not a barrier.**
- ⛔ **What this forbids you from saying.** Two claims that look obvious and are
  wrong: *"the class never declares that field, so the assignment fails"* and
  *"the assert halted the function before the next call."* Both were the stated
  mechanism for the Mod Manager screenshot defect in a third-party mod, and both
  are false while **every line that mod cited was correct** — the class really
  does derive from `ProtectedPropertyObject`, really does declare
  `ScreenshotPaths` and not `ScreenshotUrls`, and the assert really is there.
  The failure was in the "therefore". See `C52`, where the real cause turned out
  to be a `local` read outside the block that declared it, two files away.
- ⚖️ **What is measured and what is not.** SOURCE-READ 2026-08-16 at
  `ModTools\Src`; the `rawset`-after-assert shape is plain in the listing and
  `EF-008` is independently established. ⛔ **No leg has watched a
  `ProtectedPropertyObject` take an undeclared key at runtime**, and whether the
  shipped executable evaluates the assert at all (rather than compiling it out)
  is not established here — it does not change the conclusion, since both
  branches end with the write landing. Do not restate this as MEASURED.
