- ⭐ **A HUB-FILED MAINTENANCE REQUEST'S BAND LIVES IN THE QUEUE KEY, NOT IN
  THE REQUEST USERDATA.** (Source-read 2026-09-01, `BANDS_CLEAN_REVERT` delta
  17.) `DroneControl:AddBuilding` (`Lua/Buildings/DroneControl.lua:685-718`) —
  the override used by every hub, rocket and RC Rover — files each request into
  `supply_queues[p][res]` / `demand_queues[p][res]` / `priority_queue[p]` at
  `p = building:GetPriorityForRequest(request)` and **never calls
  `request:SetPriority`**; only the base `TaskRequestHub:_InternalAddRequest`
  does (`CommonLua/TaskRequest.lua:312-313`), and maintenance requests are
  created at `GameInit` BEFORE any command centre is connected
  (`RequiresMaintenance.lua:75-97`; `TaskRequester:AddRequest :125-137` loops a
  then-empty `command_centers`), so the base path never runs for them. Together
  with `EF-071` (C iterates the bound range over the queue tables): **the band C
  serves a maintenance request at is decided by WHICH KEY it is filed under** —
  moving a request between keys (`remove_entry` + append, the same ops
  `AddBuilding`/`RemoveBuilding` perform) re-bands it without touching persisted
  C-side userdata. A design that re-files through `_InternalAddRequest` instead
  WRITES a priority into the userdata that vanilla's own hub path never touches
  — avoid, or use only vanilla-legal values (opt-in bands report §4.1, 2-S).
- **Corollaries, same read:** shuttle logistics never sees the band structure —
  `LRManager` keys its queues by RESOURCE (`Lua/LRManager.lua:12-41, :51-88`);
  and `Request_UpdateDeficits` (`DroneControl.lua:121-123`, called from the
  persisted deficit thread) is a FOURTH C consumer of the hub's queue tables
  beyond `Request_FindTask` and the two finders — any design that reshapes the
  REAL tables must keep all four consumers fed (`EF-072` lists what `FindTask`
  itself passes).
