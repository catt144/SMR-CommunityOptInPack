- **The measurement, and it is a close-out failure this leg caused.** During the
  `split-optins` verification matrix (2026-08-12), cell (d) loaded `SPWITB` and
  `SPWITC` — byte copies of `CP60RT` and `Autosave Sol 311`, both on the owner's
  HELD list — and let each run. Directory state, by NAME, either side:

  | | 18:33 (before the leg) | 19:04 (close-out) |
  |---|---|---|
  | `Autosave Sol 306.savegame.sav` | present, 55,419,123 bytes | ⛔ **ABSENT** |
  | `Autosave Sol 311.savegame.sav` | present, 54,885,560 bytes | ⛔ **ABSENT** |
  | `Autosave Sol 311(2).savegame.sav` | absent | present, 55,260,969 bytes, mtime **18:52:43** |

  18:52:43 falls inside the cell-(d) process (18:50:43 → ~18:53). ⛔ **Nothing in
  the harness wrote a savegame at that moment** — the run's own writes are named
  `SPWIT*RT`, and the game wrote this one by itself.

- **The route, from Src** (`CommonLua/Savegame.lua:1484-1528`):

  ```
  Autosave(save_name)
    :1505  err, list = Savegame.ListForTag("savegame")
    :1507-1515  autosaves = every entry whose full metadata says v.autosave
    :1518-1519  SaveAutosaveGame(...)            -- the NEW file is written first
    :1524-1526  for i = (GetAccountStorageOptionValue("AutosaveCount") or 1), #autosaves do
                    DeleteGame(autosaves[i])
                end
  ```
  ⚠️ **The loop starts AT `AutosaveCount`, not at `AutosaveCount + 1`.** With the
  option at 1 and two autosaves on disk it deletes indices 1 AND 2 — both of
  them — which is exactly the two-gone/one-new shape measured above. Default is
  `const.DefaultAutosaveCount = 2` (`Lua/_GameConst.lua:18`); the option is
  account storage (`Lua/ProjectOptions.lua:331`) and is the player's to set.

- ⇒ ⛔ **THE HARNESS RULE THIS CREATES.** WORKFLOW's "runs use a designated COPY,
  never the campaign save" protects the campaign FILE. It does not protect the
  save DIRECTORY, because the copy is still that campaign and its autosave timer
  is still running. **Any leg that loads a copy of a real campaign and lets game
  time pass must, before the launch, byte-copy every autosave it could displace
  and list them by name** — the same discipline already applied to the saves a
  leg deliberately stages. A leg that only needs a static read should load at
  speed 1 and quit fast, and even that is not a guarantee.

- **What was recoverable and what was not.** `Autosave Sol 311` was restored
  byte-exact (MD5 `D5BCCF2CB758D5E5EA0706D671602AF5`, 54,885,560 bytes, original
  mtime preserved) — but only because the leg happened to have staged a copy of
  it as a witness. `Autosave Sol 306` was never copied and **is not recoverable
  from anything this leg holds**. Steam Cloud is ON (`EF-051` HOLD), so the
  owner-armed restore mechanism may or may not return it; that is a thing to
  check, never a thing to claim.

- ⭐⭐ **AMENDED 2026-08-13 (combined-sitting prep, measured on two unattended
  dry-run launches): A BYTE COPY OF AN AUTOSAVE *IS* AN AUTOSAVE TO THE
  ROTATION, AND THE ROTATION DELETES IT LIKE ONE.** The rule above says to
  byte-copy every autosave before the launch. It does not say what this leg
  measured: that **staging a copy OF an autosave puts the staged copy itself in
  the firing line**, so the protective copy and the fixture can be destroyed by
  the same sweep.
  * **The mechanism, read out of the file:** `autosave = true` lives in the
    savegame's own plain-text metadata header, and `Copy-Item` carries it
    verbatim. `Autosave()` (`:1507-1515`) builds its list from *"every entry
    whose full metadata says `v.autosave`"* — a name-independent, tag-driven
    enumeration. Header read directly, 2026-08-13: `Autosave Sol 311(2)` and
    `Autosave Sol 311(3)` carry `autosave = true`; `SPCONRT`, `SPWITCRT`,
    `SPWITBRT`, `TEST2H TRAIN`, `PT35FIXTURE`, `CP60RT` carry **no `autosave`
    key at all** — a save written by ordinary `SaveGame` never gains one, so
    the tag is inherited only by copying.
  * **What it cost, and the arithmetic reconciles exactly.** Four autosave-tagged
    files were on disk (`Autosave Sol 311`, `Autosave Sol 311(2)`, `SPWITC` — a
    copy of `Sol 311` from the split matrix — and `CSHOST`, this leg's own freshly
    staged copy of `Sol 311(2)`). Two dry-run loads of a campaign copy let the
    rotation fire: it wrote `Autosave Sol 311(3)` and deleted **three** — indices
    2, 3 and 4 — keeping only index 1. ⇒ **The leg's own fixture was deleted by
    the same sweep as the owner's held save**, and a sitting that had staged it
    the night before would have found it missing with the owner in the chair.
  * ✅ **`Autosave Sol 311` restored byte-exact** (MD5 `D5BCC…`, verified after
    restore) — the pre-copy rule worked, and this is the first time it has been
    the thing that saved a file rather than a precaution nobody needed.
    ⚠️ `SPWITC` was not pre-copied and is not recoverable from anything this leg
    holds; it is a split-optins artifact, not on any protected list, inventoried
    here rather than filed.
  * ⇒ **TWO CLAUSES THIS ADDS.** (1) **Never stage a fixture from an autosave** —
    check the header for `autosave` and copy from a `SaveGame`-written save
    instead; a fixture that can be deleted mid-sitting is not a fixture.
    (2) **Pre-copy and reconcile around EVERY launch, not just the first.**
    ⚠️ And do it because the firing is **not predictable**, not because it is
    per-load: a third launch of the same shape, minutes later, wrote no autosave
    and deleted nothing. The trigger is the campaign's own autosave timer
    elapsing while the copy runs, so two short launches can differ. Reconciling
    by name after each one costs half a second; reasoning about whether this
    launch will fire is how a file goes missing.
