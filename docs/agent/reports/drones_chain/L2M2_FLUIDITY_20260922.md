# Drones chain L2M2 — the motion re-driven the way the game's own units move

Owner authority, 2026-09-22, having flown L2M's `74b1e4a`: *"Its studdered very bad coming out,
the flight path is sorta better but still pretty sharp on the angles and its kinda glitchy /
suttery when it lands to do the repair sequence. I needs the be, natural, fluid, and respemble
flight."* The route (L2R) was not in question. This link replaced the motion layer of
`tools/devmods/train_hub/Code/30_TrainHubDrones.lua`, committed as `d77efa4` with follow-ups
`6d89b1a` (signed `BankAngle`, receipt re-measured on LF bytes) and `b84f106` (the correction
below, after the owner's first console run failed). **No game was driven by this link; fluidity
is the owner's verdict in link 3.** Every cause below is reasoned from the code and the archived
source, not measured on the rig.

## Correction after the owner's first console run, 2026-09-23

`*r SpawnHubDrone()` on `d77efa4` raised `HGE::l_SetAcceleration: Expected integer` at the first
chord (`30_TrainHubDrones.lua:572`, called from `Update`, `Sample` and the driver thread). The
cause is the engine's number model, now filed as **EF-116** (fix pack `2812098`, mirrored here
`de8a92b`): **this Lua divides an integer by an integer as integers.** Shipped code coerces first,
`party_size * 1.0 / remaining_seats` (`Lua/Factions/Factions.lua:180`), `trip_time + 0.0`
(`Lua/TransportStatistics.lua:56`), `DivAsFloats(...)` (`Lua/Factions/Legislature.lua:1344`), and
`Min`, `Max` and `Clamp` are documented integer helpers (`LuaSharedLib.lua:317-333`). So
`remaining / 1000` was `0`, the chord's acceleration was infinite, and `math.floor` could not make
it an integer. The lupa smoke runs standard Lua, divides `315 / 1000` to `0.315`, and passed.

The fix (`b84f106`): every fractional division in the flight source goes through
`div(a, b) = (a * 1.0) / b`; `math.min`, `math.max` and a local clamp replace the engine's
integer helpers; every number handed to the engine goes through `int(x) =
math.tointeger(math.floor(x + .5))`. The smoke now models the engine's numbers: `Min`, `Max` and
`Clamp` are absent from the mock globals, `point()`, `SetPos`, `SetAcceleration`,
`SetRollPitchYaw` and `Sleep` assert `math.type == "integer"`, and a static gate refuses any `/`
outside `div()`'s body. In standard Lua the planner's output is byte-identical (same fixture
offsets, chords and wakes); the receipt was re-measured for the new source hash.

**This also revises the ranking of the stutter's causes.** L2M's sampler computed
`u = Clamp((elapsed - start) / (finish - start), 0, 1)` on integer game times, so in game `u` was
`0` or `1`: `F.Position` returned span endpoints, the drone stood at each and dashed to the next
within one 100 ms prediction. That, more than the per-tick snap-and-restart, is what "stuttered
very bad" most likely was; the snap-and-restart, the 50 ms corner trim and the state re-issue
still stand as faults of that build and are still gone in this one. INFERRED from the operator,
not measured: the control is the owner's one console line below.

**Control for the owner, before flying anything:** `*r print(7/2, 7*1.0/2, math.type(7/2))`. If
EF-116 holds it prints `3  3.5  integer`; if it prints `3.5  3.5  float` the fact is wrong, the
error had another cause, and link 3 stops on it.

## The reference: what a vanilla Wasp calls, how often, and what it leaves to the engine

SOURCE, installed build **24995074**, archived **1.1.0.403908**
(`B:\Dev\SMR\SMR-Shared\SMR-SrcArchive\1.1.0.403908\Src`):

- A Wasp's flight is a **game-time command thread** that calls `Flight_Step` and then
  `MoveSleep(status)` for the time the C++ component returns (`Lua/Flight.lua:1046-1066`;
  `FlyingDrone:MoveSleep` → `Drone:MoveSleep` → `Sleep`, `Lua/Units/FlyingDrone.lua:87-89`,
  `Lua/Units/Drone.lua:1744`). Its class moves in `step = 4*guim` increments with
  `max_sleep = 333` and `move_speed = 16*guim` (`Lua/Units/FlyingDrone.lua:36-39`,
  `Lua/Flight.lua:805-806`): one Lua wake per 4 m, about every 250 ms at cruise, never a write
  per frame. Between wakes the engine owns the interpolation.
- Its landing is **one decelerating engine move, then the state change**:
  `GetAccelerationAndTime(dest, 0, dh)`, `SetPos(dest, time)`, `SetAcceleration(accel)`,
  `MoveSleep(time)`, `LandingEnd()` (`Lua/Units/FlyingDrone.lua:181-202`); `LandingEnd`
  resets the acceleration and sets `idle` only after the move has ended (`:124-132`).
- The shipped rail ride in this game, the train, moves the same way along scripted points:
  `SetPos(spot_pos, move_time)` + `SetAcceleration(accel)` per element from a game-time thread,
  with timed `SetRollPitchYaw(0, pitch, yaw, dt)` for orientation
  (`Lua/Units/Train.lua:512-513`, `:549-550`, `:585-586`, `:495`).
- Every flight parameter, including `hover_height` (7 m), is **class-static, snapshot in C++;
  "per-instance overrides are ignored by design"** (`Lua/Flight.lua:149-160`). The solver's
  path is its own spline (`avg_spline_dist = 30*guim`) over the flight height cache, which is
  terrain plus marked objects (`Lua/Flight.lua:213-323`), arriving at rest at a single `dest`.
- `SetCurvature(true)` / `GetCurvatureTime` have **no caller in shipped Lua**
  (`grep -rn "SetCurvature\|GetCurvatureTime" Lua/ CommonLua/ --include=*.lua`, docs excluded:
  zero hits). `SetAcceleration` and `GetAccelerationAnd*` are used by rockets, shuttles,
  crystals, diggers and trains.

**The finding:** L2M's `F.Update` ran from a **real-time** thread every 20 ms and, on almost
every tick, first snapped the drone to the curve (`if a.predicted ~= elapsed then
drone:SetPos(pos) end`, an instant write that fired whenever the previous 16-33 ms prediction
missed) and then restarted a new 16-33 ms interpolation. A vanilla Wasp does neither.

## The three faults, their causes, and what changed

| fault (owner's order) | cause, reasoned from `74b1e4a` | change in `d77efa4` |
|---|---|---|
| **Bad stutter coming out of the pit** | Per-tick snap-and-restart above, worst where speed is highest: the under-deck run at `Speed=6000` (60 m/s) moves 0.6 m per 10 ms of tick jitter, so every mistimed tick showed as a visible jump, at the 40-50 Hz a 20 ms real-time sleep gives on a 120 fps rig. Also `SetState("fly")` was re-issued at every waypoint (`a.drone:SetState(step.state)` on each segment change), restarting the fly animation at each corner. | One timed `SetPos(dest, ms)` + `SetAcceleration(a)` per chord, at most 333 ms, issued exactly when the previous chord ends by a **game-time driver**; no per-frame write, no snap after the placement at spawn. `SetState` only when the state actually changes. |
| **Corners still sharp** | The trim was `TurnRadius / speed` = 300 / 6 units per ms = **50 ms** either side of a corner (3 m at 60 m/s), and the blend inside it took the drone from 15 m/s vertical to 60 m/s horizontal: about 60 g. The rounding existed but was too small to see and the speed change across it was violent. | A quadratic Bezier inside the corner's own two legs, trimmed up to `TurnRadius=1500` (15 m) or half the shorter leg, **flown at the speed its radius allows under `Accel`** (v² = Accel × radius); straights run a trapezoid between their corner speeds. The crest reversal passes through rest with the same acceleration on both sides (a parabola, not a stall). |
| **Glitchy landing into the repair** | Cubic braking to the work origin, then the construct state, animation and FX at the segment change, while yaw and roll were still settling through their own interpolation; plus the snap-and-restart above on the descent. | The final descent decelerates to **zero speed and zero roll** at the pose; the state, animation and FX change only at that chord's end, in vanilla's `Land → MoveSleep → LandingEnd` order; roll targets are zero on every straight so the drone is level before it stops. |

## Mechanism, decided leg by leg

Engine-owned: **ComponentInterpolation** through timed `SetPos` (the chord), **acceleration**
through `SetAcceleration` (the speed within the chord), and rotation through timed
`SetRollPitchYaw`. Call path: game-time driver thread → `SMROptInHubFlight.Sample` →
`F.Update(record, now)` → `issue()` → `drone:SetPos(step.bp, remaining)`,
`drone:SetAcceleration(acc)`, `drone:SetRollPitchYaw(roll, 0, yaw, remaining)`.

Scripted: the route (unchanged), the corner geometry, the speed profile and the chord cut.

Not adopted, with the call path that would reach it: `FlyingDrone:Goto` →
`FlyingObject:FlightGoto` → `Flight_Step`. Its hover height and move parameters are class-static,
its path is the solver's own spline over the terrain height cache, and it arrives at rest at one
destination; it cannot ride a rail at +15 m through hoods, duck a deck or follow a track bend.
Stop 1 fired for that path and the brief's fallback was built instead: the best hand-driven
motion, changing the driver, the profile and the landing, not only the corner radius.
`ComponentCurvature` stays off (`SetCurvature(false)`) because no shipped Lua calls it and its
arc cannot be measured; keeping every chord a straight line is what the clearance receipt bounds.

| leg | mechanism |
|---|---|
| Pit column (floor → rim → crest) | One straight: trapezoid 0 → `ClimbRate` → 0 under `Accel`, about 3.3 s for 30 m; yaw pre-turns toward the lane while rising (look-ahead heading, rate-limited to the Wasp's `max_yaw_speed`, 150°/s). |
| Crest reversal | A stop node: the rise decelerates to rest and the descent accelerates away with the same magnitude, so acceleration is continuous through the crest. A spawn-then-send hover is a dwell at rest, not a stall. |
| Crest → lane corner | Bezier trimmed 3.5 m (half the 7 m descent), flown at about 5.4 m/s; no bank (vertical plane). |
| Under-deck run | Straight: accelerates to about 28 m/s and brakes for the outside corner within the 90 m; chords 22-319 ms. |
| Outside climb, top corner, transfer | 11 m trims at both ends of the 22 m climb (about 9.7 m/s); transfer straight at up to `Speed`. |
| Transfer → rail drop | Two 5 m trims make the 10 m vertical drop an S-curve at about 6.5 m/s. |
| Over-track cruise | Element waypoints; collinear elements need no rounding, bends are rounded up to half an element leg and slowed by their radius; roll follows the horizontal turn rate. |
| Descent to fix height | Rounded corner into a straight descent that reaches the work origin at rest and level. |
| Work | At rest; `constructStart` / `constructIdle` / `constructEnd`, FX `Construct` on the target, exactly at the chord end. |
| Return | The same nodes reversed, same profile (within chord rounding), then the column and a decelerating landing; `LandingEnd` at `removed`. |
| Hidden tunnel legs | A concealment seam is a **sharp node**: the chord ends on it exactly, the direction change is hidden, speed is continuous; no stop at the mouth. |
| Early recall | Brake at `Accel` along the planned chords, stop, fly the flown chords back with the same caps; no new chord across a rounded corner. |

## Time, the deadline fence, AI and save

The visual's own duration now defines its offsets: `arrival - started`, `work_done - started`
and `removed - started` come from the profile (fixture: **25524 / 31524 / 57051** game ms,
against L2M's 10981 / 16981 / 27962). The fence holds by construction: the game-time driver
issues each chord when the previous ends; a sparse or late sampler (L4 after a rearm, a long
frame) snaps once to the absolute position and flies the current chord in its remaining time,
never extending a deadline. A repeated `now` issues nothing. L4 still owns persisted deadlines
and derives the visual start from them and the plan offsets; nothing new is persisted.

SAVE (FIX_POLICY §3a, layer 1, stated in the file header): the driver is a mod-owned game-time
thread with zero upvalues and the orphan gate `if not SMROptInHubFlight then return end` as the
first statement after its only yield; `OnMsg.SaveGameStart` deletes it with every visual before
the persist walk and gates spawns until `SaveGameDone`. This is a declared departure from L2's
"REAL-time driver" header; the A/B and long-interval soak §3a asks for are link 3's and link 5's
live checks (save cancellation and relaunch, autosave mid-trip).

AI suppression is unchanged: `init_with_command = false`, no `Goto`, `FlightGoto`, `SetCommand`
or `UseBattery`; the smoke makes those throw. Battery is topped up at every wake.
