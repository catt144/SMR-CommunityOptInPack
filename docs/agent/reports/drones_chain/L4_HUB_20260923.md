The design decisions that were mine: the deadline's distance is the straight line from the hub to
the break, not the along-track distance, because the engine flies the leg straight and the visual
should not arrive long before its deadline; the fleet tier metric is vanilla's own `GetDroneLoad`
word, exactly the words the owner used; one repair launches per tick so the pit is not crowded; a
waiting repair recalls a fleet drone without the delay because a repair outranks a standing
drone; the recall never touches a busy drone or one carrying a cube.

## Owner, in play, 2026-09-23: "our drones started resource balancing the stations connected to our network"

The dev mod loads from this working tree, so the remote-station registration was live in the
owner's game as soon as it was written. `AddCommandCenter` files EVERY request of the station with
the controller (`TaskRequestHub:AddBuilding`, `CommonLua/TaskRequest.lua:298-306`), the storage
supply and demand requests included, so the fleet began hauling between stations: not track work
by the 2026-09-19 ruling. Fixed in `b556035` before it was committed: a controller asks the
building before filing each request, `building:ShouldAddRequestToCommandCenter(request, center,
res)` (`DroneControl.lua:742`, `:754`), declared once on `TaskRequester` as `return_true`
(`_TaskRequest.lua:209-210`) and not by `Station`; a chained override on `Station` answers false
for a train hub that is out of range unless the request is the station's maintenance material or
maintenance work request, and hands every other case to the captured original. A station inside
the radius keeps vanilla's full service. Stations registered before the filter carry every
request until the next load, when each out-of-range one is re-filed once. **The owner's running
game keeps balancing until it is restarted or a save is reloaded.**
