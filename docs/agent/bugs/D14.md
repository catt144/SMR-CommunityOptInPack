### D14 — Train hub dev build audit `[open — save defect; siding deadlock fixed]`

Dev-only content module, not a shipping module. Authority: owner 2026-09-23,
the train audit brief; confirmed defects in the dev mods may be fixed by the active sitting.

**(a) Global dwell hook displaces the native waiter's save permanent.** On archived
1.1.1.405907, `CommonLua/Core/cthreads.lua:466-478` registers the current global
`WaitWakeup` as `cthread.WaitWakeup`. The old hub hook replaced that global but
delegated to its captured native C function. Suspended native wait frames therefore
lost that mapping. `DroneControl:UpdateDeficits` (`Lua/Buildings/DroneControl.lua:129`)
and `MarkFlight` (`Lua/Flight.lua:835`) both wait there; either can be the first
persist traversal to encounter it. Neither stack identifies the owning defect.
The save error is measured in the owner's logs; this mechanism is reproduced by
the archived collector in `tests/dwell_smoke.py`, not by a native save in this audit.

**Withdrawn repair `3a0faff`:** stop replacing the global. Copy the two train commands from archived
1.1.1.405907, changing only the hub's timeout; foreign stations call the captured
original. No new persisted key or changed key. The command copies use save-policy
layer 2; native saves and removal behaviour have not been tested here. Existing
placed-hub removal remains unsupported under FIX_POLICY §0.

The withdrawn repair passed `dwell_smoke.py` while the `d73d701` control failed
its native-permanent assertion. That test did not cover legacy serialization.
`move_smoke.py` checks elapsed boarding time, minimum wait, foreign station/thread
and live tuning on the 1.1.1 source. A replacement save repair must cover native
old→new→save→reload; a fresh-process save logging the same error falsifies it.

**Owner follow-up, 2026-09-24:** old autosave and known-good templates assert in
`luaSPersist.cpp:1272`, then crash after Ignore All. `3a0faff` also changed the
existing `cthread.WaitWakeup` mapping from Lua closure to C function; the test
missed old-save compatibility. Restored the exact legacy dwell section from
`d73d701` as containment. Its original save defect remains, and `dwell_smoke.py`
was RED again after rollback. The owner then loaded the version-15 template and `Autosave Sol 31(3)`
without assertions (`10.45.34` and `10.49.56-6aad2d75.log`); both processes exited
normally. The later autosaves still log the original C-function persist error.
Input saves were backed up, not rewritten or certified repaired. The report's
§8 preserves logs, backup locations, the limited type-mapping proof and migration
obligations. Dev version alone cannot distinguish the old/new waiter mapping.

**Snapshot-guard candidate, 2026-09-24:** the owner proposed removing our change
at save time and restoring it at load. The implemented narrower guard chains
PersistGame, restores the native waiter only around its snapshot, and restores
the runtime wrapper on success, returned error or thrown error. New metadata
`SMROptIn_hub_native_waiter=1` chooses the native mapping before EngineLoadGame;
unmarked existing hub saves retain their legacy Lua mapping. The wrapper body
itself is unchanged. Saves without a hub mod record select the native mapping.
Pre-wrapper hub saves are an older ambiguous case, not guessed by mod version.
The updated dwell smoke tests archived snapshot/collector bodies and rejects
broken snapshot and legacy-load mappings. Native legacy-load→new-save→reload,
including an autosave, is pending; D14(a) remains open. Report §10 holds scope,
controls and the required native result. This does not unload buildings or erase
saved command frames.

**(b) Cross-map graph ownership — design decision open.** `HubTrackGraph` follows
any reciprocal TrackTunnelBase.linked_obj; `register_remote_stations` then adds
the hub controller. `30_TrainHubDrones.lua`'s stock FlightGoto receives XY on the
drone's current map. A shaft can therefore enroll unreachable stations and
schedule repair visuals on the wrong map. The scope of the owner's network-wide
rule needs a map ruling, OI-27; no restriction was silently added. Control: a hub
connected through a shaft, with a far-map station, must be compared against the
same-map tunnel case. No such fixture ran in this audit.

**(c) Nanite completion early return — conditional source risk.** Archived
1.1.1.405907 `Lua/Buildings/ConstructionSite.lua:2673-2675` can return without
completing a queued leader. The hub's `complete_job` pays first, calls Complete,
and returns done unconditionally; discovery can see the still-live leader again.
Control: put a real repair leader into the vanilla nanite completion path and
check payment once, with the ordinary-completion case beside it. Not established
as the owner's incident and not fixed without that reachability check.

**(d) Split after discovery — conditional source risk.** The 1.1.1 track split
body in `TrackElement.lua` retargets repair sites to their new tracks. The hub's
pending job caches its original track and `job_for_site` suppresses rediscovery
of that leader. A waiting job may stay gated on a stale track reference. Control:
discover a short-stock job, split/salvage the track while its site survives on
the connected side, replenish stock, and compare with an unsplit track. Native
reachability/result remain open; no claim that this happened in the stalled save.

**(e) Imported EntitySpec load path.** All three evening logs contain the
ArtSpecEditor.lua:573 nil EntitySpecPathToEntity error. That method body is
unchanged between archived 1.1.0 and 1.1.1; the definition is in SceneImport.lua,
unavailable on the observed retail load. Ownership is vanilla's editor/mod-load
path reached by our imported source data, not a train/repair command. Art/import
changes were outside the audit. Control: isolate the hub entity import on a fresh
retail load and preserve editor round-trip behavior; no global editor-API stub.

**(f) Siding departure deadlock — fixed; owner confirms trains unstuck.** Native
reads on hub 6430 found opposite parked pairs waiting to depart through each
other's connector: slots 1↔2 and 3↔4. All connected tracks could run, route
membership held, command threads were live and both crossing records were clear.
The exit-contact guard from `2606719` predates the owner's later off-line siding
design (`99a8cd9`; spec §9). It still treated a siding reservation as occupying
the running rail. Earlier records had noted mutually blocked departures as a
limitation; the later siding implementation had not updated that guard.

`HubExitClear` now exempts only a train parked at this hub with the matching
arrival slot and no crossing ownership. Unknown, incoming and moving reservations
still block; native outgoing-track exclusion and crossing serialization remain.
No routing/queue policy or persisted name changed. The paired-siding regression
in `move_smoke.py` passes and fails against `2035dbb`'s guard. After restarting
with the correction the owner reported, "They are now unstuck." Native visual
clearance was not explicitly confirmed; this is the observed colony, not every
layout. Details, members and controls are in the report's §9.
